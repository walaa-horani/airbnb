Section 5 of 5 — Host Onboarding & Auth Flows

How hosts connect Stripe & PayPal, and how Clerk auth integrates with Convex

Stripe Connect Express Onboarding
1
Host clicks "Connect with Stripe"
On /host/onboarding/stripe or dashboard banner. Convex action calls accounts.create → Express account.
2
Stripe hosted onboarding
Redirect to Stripe's hosted UI. Host fills bank details, identity, tax info. Return URL back to /host/dashboard.
3
Webhook confirms status
account.updated webhook → Convex HTTP endpoint → updates stripeAccounts table. chargesEnabled: true = fully active.
4
Dashboard shows progress
Status pill: Pending → Restricted → Active. Host can't receive bookings until chargesEnabled is true.
PayPal Marketplace Onboarding
1
Host clicks "Connect with PayPal"
Convex action calls Partner Referrals API v2 → generates onboarding link with PAYMENT + REFUND permissions.
2
PayPal hosted sign-up
Host redirected to PayPal to create / link their PayPal business account. Return URL back to /host/dashboard.
3
Merchant status confirmed
MERCHANT.ONBOARDING.COMPLETED webhook → Convex endpoint → saves paypalMerchantId + status active.
4
PayPal appears at checkout
Only shown to guests when the property's host has an active PayPal account. No PayPal account = Stripe only shown.
Clerk ↔ Convex Auth Integration
1
Clerk configured with proxy
No middleware.ts file. Instead, Clerk proxy routes set in next.config.ts rewrites. Auth checked via auth() in Server Components and Route Handlers.
2
User signs up (Google or Email)
Clerk handles the full auth UI at /sign-in and /sign-up using Clerk's hosted components. Role defaults to guest.
3
Clerk webhook syncs user to Convex
user.created + user.updated → Convex HTTP endpoint at /api/webhooks/clerk → upserts users table with tokenIdentifier.
4
Convex uses tokenIdentifier for all auth
Every protected Convex function calls ctx.auth.getUserIdentity() → looks up user by tokenIdentifier. Never trusts a userId passed from the client.
